# 地图任务 Agent · v2.4（百度地图开发者大赛）

一句话任务 → 大模型（文心 ERNIE）拆成结构化约束 → 百度地图 Web 服务 API 取事实（地理编码 / 地点检索 / 批量算路 / 路线规划）→ **确定性编排器**选酒店、排日程 → 手机框 UI 可视化、可拖拽、改动前后对比后批准。

演示场景 1：下周一到周二去上海出差，拜访三家客户（上海中心大厦 / 静安嘉里中心 / 港汇恒隆广场，写字楼和地址真实，公司名为示例），晚上想打网球、去个酒吧，酒店预算 800 以内。

演示场景 2（v1.3）：用户自己点名酒店、地点和时间——「10月5日去上海，住上海虹桥家庭酒店。当天下午1点去仙霞网球场打球，打完回酒店，下午5点去浦东美术馆看展，再回酒店。第二天早上9点去仙霞网球馆打球，中午12点去旗忠网球中心看网球比赛。」→ 不选酒店、不重排，只核对地点、算每段打车/公交用时、查时间冲突。

> v1.1 已用真实百度 AK + 千帆 ERNIE 跑通全流程（见第 7 节）。没有 Key、`MOCK=1`、或百度返回 `status != 0`（例如 240「APP 服务被禁用」）时，每个接口自动换成**示例数据**（响应带 `mock:true` 和 `reason`），整条流程照样能走完；页面顶部徽章显示「示例数据 / 真实数据」，过程日志每一步都写明原因。

## 1. 运行

需要 Node ≥ 18（用了内置 `fetch`），没有第三方依赖，不用 `npm install`。

```bash
cd /workspace/hackathons/builds/baidu-task-agent
# 示例数据模式（不需要任何 Key）
MOCK=1 node server.js                # → http://localhost:8890
# 真实模式：Key 只放环境变量
export BAIDU_MAP_AK=...               # 服务端 AK（必需，用于地点/算路/路线/地理编码）
export BAIDU_MAP_BROWSER_AK=...       # 浏览器端 AK（可选，有了才显示真正的百度地图）
export QIANFAN_API_KEY=...            # 千帆 API Key（文心 ERNIE，可选）
export QIANFAN_MODEL=ernie-4.5-turbo-128k   # 可选，默认就是它
node server.js
# 后台常驻
MOCK=1 setsid nohup node server.js > server.log 2>&1 < /dev/null &
```

其它可选环境变量：`PORT`（默认 8890）、`BAIDU_MAP_SK`（AK 选了 sn 校验时填，未实测）、`QIANFAN_BASE_URL`（默认 `https://qianfan.baidubce.com/v2`）、`QIANFAN_JSON_MODE`（默认 `json_object`，可试 `json_schema`，不支持时自动退回）、`OPENAI_API_KEY` / `OPENAI_MODEL` / `OPENAI_BASE_URL`（备选厂商）、`LLM_PROVIDER=qianfan|openai`（强制指定）。

Key 只从环境变量读，不写文件、不进日志、不回给前端。唯一例外是浏览器端 AK，它本来就要放进页面里加载 JS 地图（请在百度控制台给它设 Referer 白名单）。

检查 Key：

```bash
bash scripts/check-keys.sh    # 百度地点检索 1 次 + 大模型 1 次，只打印 OK/FAIL 和状态码
```

## 2. 用到的 API 和 AK 类型

| 功能 | 接口 | AK 类型 | 在哪用 |
|---|---|---|---|
| 地理编码 | `geocoding/v3` | **服务端 AK** | 客户地址 → 坐标 |
| 地点检索（圆形区域） | `place/v2/search`（`location`+`radius`+`radius_limit`，`scope=2` 拿评分/价格/营业时间） | **服务端 AK** | 酒店候选、网球/酒吧/餐厅、任务雷达 |
| 批量算路 | `routematrix/v2/walking` / `driving` / `riding`（每次 ≤ 50 条 OD，后端自动分批） | **服务端 AK** | 酒店 × 客户通勤、日程点两两通勤 |
| 路线规划 | `direction/v2/driving`、`direction/v2/riding`、`directionlite/v1/walking` | **服务端 AK** | 时间轴地图上的真实折线 |
| 公交/地铁路线（v1.3） | `direction/v2/transit`（带 `departure_date` / `departure_time`） | **服务端 AK** | 场景 2 每段的公交/地铁用时、线路、票价 |
| 地点核对（v1.3） | `place/v2/search`（`region` + `city_limit`） | **服务端 AK** | 用户点名的酒店/场馆 → 百度 POI |
| JS 地图 | JavaScript API GL（`api?v=3.0&type=webgl&callback=…`，回调式加载，不走 `document.write`） | **浏览器端 AK** | 雷达圈、酒店/客户点、编号路线、变更审批小地图 |
| 大模型 | 千帆 v2 `chat/completions`（OpenAI 兼容，Bearer 鉴权），默认 `ernie-4.5-turbo-128k` | 千帆 API Key | `/api/parse` 任务解析、`/api/replan` 变更 diff |
| 网页搜索（v2.4） | 千帆「百度搜索」`POST qianfan.baidubce.com/v2/ai_search/web_search`（`top_k 8`，`search_recency_filter: month`） | 千帆 API Key（同上） | 场景 3「近期热点」：只找活动名和日期，场馆再用百度地点检索核对 |

百度控制台要做的事：创建「服务端」应用 → 勾选 **地点检索、地理编码、批量算路、路线规划** 服务 → IP 白名单填本机出口 IP（测试可 `0.0.0.0/0`）。如果返回 `status 240 APP 服务被禁用`，就是服务没勾选。

千帆结构化输出：按千帆文档，`response_format: json_schema` 目前只对 DeepSeek / GLM / Qwen 等部分模型开放，ERNIE 用 `json_object`；所以后端把 JSON Schema 写进系统提示词，返回后在本地按 schema 校验，不合格就退回规则解析并在日志里写原因。模型只负责理解和出 diff，**不定时间、不定距离、不点名店铺**。

## 3. 后端接口（`server.js`）

| 接口 | 说明 |
|---|---|
| `GET /api/status` | 各 Key 是否设置、模型名、最近一次百度调用状态 |
| `POST /api/parse {text}` | LLM：自然语言 → 结构化任务（客户名称/地址/日期/时间窗、活动、酒店偏好、按钮式追问、假设） |
| `GET /api/geocode?address=&city=` | 地理编码 |
| `GET /api/poi?query=&center=lat,lng&radius=` | 圆形区域地点检索，统一成 `{name,lat,lng,rating,price,hours}` |
| `POST /api/matrix {mode,origins,destinations}` | 批量算路，返回 `rows[i][j] = {m, s}` |
| `GET /api/route?origin=&destination=&mode=` | 路线折线 `[[lng,lat],...]` |
| `GET /api/place?name=&query=&kind=&city=` | v1.3：点名地点核对。百度检索 → 本地去重（子 POI 如「北门/大堂/停车场」并回主地点）和相似度判断 → 不确定时让 ERNIE 从候选里挑（exact/alias/homophone/guess）→ 返回 `{pick, match, note, candidates}` |
| `GET /api/transit?origin=lat,lng&destination=lat,lng&date=YYYYMMDD&time=HH:MM` | v1.3：公交/地铁用时、公里数、票价、线路、步行米数 |
| `GET /api/route?…&waypoints=lat,lng\|lat,lng` | v2.3：驾车途经点路线，额外返回每段 `legs[{s,m}]`、`taxiFee` |
| `POST /api/trip {create,plan}` / `GET /api/trip?id=&k=` | v2.3：拼车行程存取（`data/trips/`），读的时候不返回 key |
| `POST /api/tripEvent {id,key,type,idx}` | v2.3：司机上报 出发了 / 接到 X 了 / 到了 / 重置；对下一段实时重算路线 |
| `POST /api/hot {city,dates,words}` | v2.4：近期热点。千帆百度搜索（每个日期段 1 次，说了运动再加 1 次；按查询缓存 1 天、存 `data/hot/`）→ ERNIE 抽活动（按来源 URL 集合缓存）→ 代码校验（日期覆盖、来源 60 天内、名称在原文里出现、去重）→ 场馆百度核对；返回 `search{calls,cached,month,cap,free}` 计数 |
| `POST /api/themes {city,dates,interests,pace,events}` | v2.4：ERNIE 出 2–3 个主题（类别只能从固定分类菜单里选），代码校验，不合格退回规则主题 |
| `POST /api/replan {text,plan}` | LLM：一句话改动 → 结构化 diff（replace/add/remove + 检索词 + 时间窗 + 放在哪） |

每个响应都带 `mock`、`reason`、`api`、`ms`；成功的百度结果在内存里缓存，省配额。

## 4. 编排器（`public/planner.js`，浏览器和 Node 共用，不用大模型）

- **酒店**：先过滤（预算、评分 ≥ 4.3、单程通勤 ≤ 60 分钟），再打分 = 通勤 50% + 评分 30% + 价格 20%；通勤来自批量算路（直线×1.3 ≤ 2km 用步行，否则驾车）。
- **地点**：先按半径（1/2/3km）和营业时间（能否覆盖活动时段，跨夜也算）过滤，再按评分排序，同分按距离。
- **行程**：客户时间窗是硬约束（到不了标红）；活动有最早开始/最晚结束；中间点 ≤ 7 个时全排列求最小通勤，新加地点用最便宜插入；拖拽后立即重算交通和时间。
- **变更**：LLM 给 diff → 算法按「中心点 × 半径 × 营业时间」检索并选评分最高的 → 生成改后日程 → 前后对比（删了什么、加了什么、结束时间、路程、通勤、受影响项数）→ 批准才生效。

## 7.2 v1.3 实测（2026-09-29，场景 2：点名酒店 + 点名地点 + 固定时间，真实百度 + 真实 ERNIE）

- 千帆充值后恢复：直连最小调用 HTTP 200（约 2 秒）。场景 2 的任务解析由 **文心 ERNIE** 完成（过程日志「理解任务 · 大模型结构化输出 · 文心 ERNIE」，约 25–35 秒），没有走规则解析；酒店名核对也调了一次 ERNIE。
- 解析结果新增 `stops[]`（名称、检索词、类别、日期、开始时间、时长、时长是否假设、之后是否回酒店）和 `hotel.name`。点名了酒店就跳过酒店检索和打分，直接核对这一家。
- 地点核对（真实百度）：「上海虹桥家庭酒店」百度没有同名店 → **上海虹桥嘉廷酒店(娄山关路地铁站店)**（长宁区天山路1111号，ERNIE 判断「家庭」与「嘉廷」同音，页面标「请确认」并列出其它候选）；「仙霞网球场」「仙霞网球馆」→ 同一处 **上海仙霞网球中心**（虹桥路1885弄，页面注明按同一处算）；**浦东美术馆**（滨江大道2777号，名称一致）；「旗忠网球中心」→ **久事体育场馆旗忠网球中心**（闵行区元江路5500弄）。
- 编排：用户给的时间是硬约束，顺序不重排；「打完回酒店」生成中途回酒店的项，显示到达时间、可休息多久、最晚几点出发；每段同时给打车（`direction/v2/driving`）和公交/地铁（`direction/v2/transit`，按当天出发时间）；路段用时以路线规划为准，和地图折线一致。
- 检查：余量 < 15 分钟标「很紧」，赶不上标冲突，公交赶不上标「坐地铁赶不上」。实测第二天 9:00–11:00 打球后打车去旗忠约 60 分钟，余量 0 分钟（有一次实测 62 分钟会迟到 2 分钟）；公交/地铁要 104 分钟，赶不上 12:00。
- ERNIE 输出的确定性修正（日志写「本地校验补全」）：把 stops 重复进 activities 的去掉；用户没说时长却标成非假设的改成假设（网球 2 小时、看展 2 小时、看比赛 3 小时），并补追问；「看网球比赛」归为观赛而不是打网球；去掉「是否工作日」这类追问，由代码判断国庆假期。
- 地图：总览一天一种颜色（蓝 = 第 1 天，粉虚线 = 第 2 天）。实测百度 GL 在 11 级以下（10 级瓦片）会把市区里的折线盖住（瓦片到齐后折线消失，颜色/线型/简化折线都没用），所以点名地点的行程总览地图加高，并用 `minZoom: 11` 适配；万一还是低于 11 级，就全部画虚线，瓦片到齐后再重挂一次折线。叠 SVG/DOM 层会让 GL 画布在 headless 下变白，所以不用。
- 旧的出差演示照常：`scripts/shoot.py` 真实模式 37 次调用、0 次降级，ERNIE 解析和变更都是真实调用。`MOCK=1` 下场景 2 也能走完（规则解析 `parseFixedTrip` + 示例地点 + SVG 示意底图）。

## 7.3 v1.4 实测（2026-09-30，分步追问：日期 → 客户在哪 → 酒店偏好，真实百度 + 真实 ERNIE）

- 用户反馈：只说「我要出差去上海见3个客户」时，旧版只追问日期和酒店偏好，没问客户在哪；但酒店要围绕客户中心点选，客户位置不定就不该搜酒店。

## 7.4 v2.0 · M1 统一任务模型（2026-09-30，按 `hackathons/library/baidu-maps/agent-flow-v1.md` 实现）

**思路**：大模型只负责「把原话翻译进栏目」，**该问什么、按什么顺序问、是哪种场景**全部由代码算（`public/slots.js`，浏览器和 Node 共用，纯函数，不调接口）。

- **5 个栏目**：锚点（客户/场馆/酒店）· 时间（日期、到达时段、空闲分钟）· 要找的东西 · 偏好 · 缺口；每项带状态 **已订 / 点名 / 没定 / 要推荐 / 待问**。任务页顶部「🧭 场景 …」卡片实时显示 5 栏和状态（回答追问后跟着变）。
- **场景模板表**（`Slots.TEMPLATES`，加场景 = 加一行）：1 出差见客户 `client_hub` · 2 定好时间的行程 `fixed_sequence` · 3 开放式 `theme_cluster`（M5）· 4 拼车 `pickup_chain`（M4）· 5 碎片时间 `time_box`（M3）· 0 通用。每行写了必填项、追问顺序、空档阈值（60/45/20/提前 10 分钟）。
- **场景识别**：ERNIE 给 `scenario_guess`，代码用原话硬信号确认（客户/拜访 → 1；有固定时间的点名地点 → 2；开车接/顺路带 → 4；「有 X 小时空」→ 5；多待/玩玩/出主意 → 3）。**模型猜了但原话没信号就不采信**（实测「晚上和朋友吃个饭」模型猜「碎片时间」→ 按通用流程）。都没信号 → **一道选择题**（5 个选项），选完带着场景提示重新解析。**混合**（周一二见客户 + 周三四多待两天玩）→ 按天拆成两段、共用酒店。
- **追问规则**（代码算缺口，说过的跳过）：日期 → 锚点（客户在哪）→「定了没」→ **酒店订好了吗** → 酒店偏好。
  - **定了没**：说了要做但没说在哪（「晚上和朋友吃个饭」）→ 先问「定好地方了吗？」：定了 → 填名字，百度核对，变成点名地点，不再推荐；没定 → 状态改为「要推荐」，锚点定了再在附近找。原话里有「想/去个/找个/推荐」的（旧演示「想打网球、去个酒吧」）直接算要推荐，不问。
  - **酒店订好了吗**（原话没点名酒店、没给预算时一定问）：订好了 → 填名字 → 百度核对 → 当每天的起点终点；还没订 → 偏好（可跳过），等地点都定了按中心推荐，**只给跳转链接（百度详情 / 携程 / 飞猪按店名搜索），不代订**；不住酒店 → 填住处/出发点，核对后当起点终点。
  - **用户给的时长覆盖默认**：「1点到2点」「13-14点」「四五点」「打1小时」→ 时长按用户说的，标「你给的时长」，不再追问「时长多久」（模型常问，代码过滤）。
- **ERNIE schema 增量**：`scenario_guess`、`time{arrive_part, free_budget_min}`、`people[]`（拼车用）、`stops[].end/status`、`activities[].status`、`hotel.status`；新枚举都有默认值，缺失的嵌套对象本地补 `{}`，不会因为模型少给字段退回规则解析。
- **地点核对修正**（实测发现的误判）：
  - 分店要对上：「外婆家(来福士广场店)」旧版判成百联徐汇店「名称一致」→ 现在分店不同降分，标「请确认」；检索时括号换成空格（百度对括号分店名检索很差，「小杨生煎(黄河路店)」只回「晓燕生煎」）。
  - 区域要对上：「上海静安香格里拉大酒店」旧版判成浦东香格里拉「同一地点」→ 现在区域词冲突降分，交给大模型/标请确认。
  - 大模型选的候选和原话品牌一个字都不沾（「外婆家」→「巴奴毛肚火锅」被判同音）→ 不采信。
  - 说了分店但几家分店同样匹配（全季人民广场 南京路/福州路/北京西路）→「好几家分店都叫这个 · 请确认」。
- 其它：节假日追问一律由代码出（实测 ERNIE 说「10月5日是国庆后上班第一天」）；原话只有一个日期时按一天（ERNIE 有时给两天）；模型编的 `other` 活动（「待定活动」）去掉；「吃个饭」也算提到吃饭。
- 实测（`python3 scripts/shoot_v2m1.py http://localhost:8890 real-v2-M1-`，真实百度 + 真实 ERNIE，截图 `shots/real-v2-M1-*.png`）：
  - 「帮我安排一下」→ 场景不清楚 → 只显示一道 5 选 1；选「出差见客户」→ 重新解析 → 日期 → 客户在哪（至少 1 个）→ 酒店订好了吗。
  - 「10月8号去上海，晚上和朋友吃个饭」→ 通用流程：定了没 → 酒店订好了吗；点开始被拦（「先说一下地方定了没」）。填「老吉士酒家(天平路店)」→ 百度 exact（天平路41号）；酒店「上海静安瑞吉酒店」→ exact（北京西路1008号）→ 规划 9 次接口 0 示例：18:30 吃饭，之后回瑞吉。
  - 「下周一周二去上海见两个客户，周三周四多待两天玩玩…」→ 场景 1，按天拆：10/05、10/06 出差见客户 ｜ 10/07、10/08 开放式安排。
  - 旧出差演示：场景 1，客户 3 个点名、网球/酒吧「要推荐」、酒店「要推荐 ≤¥800」，不插任何追问。

## 7.7 v2.3 · M4 场景 4 多人拼车接送（简化版，2026-09-30）

- 入口：一句话「周六小王开车从漕河泾开发区出发，先到徐家汇接我，再去静安寺接小李，一起去旗忠网球中心看比赛，12点前到，回来反过来送」→ 代码识别为场景 4（「开车…接」「先接/再接」「反过来送」是最强信号，优先于「12点前到」这种固定时间）→ 只问一步「谁开车、在哪接人、几点到」（司机 / 出发地 / 每个人在哪上车 / 目的地 / 几点前到 / 回程要不要送，原话有的预填；`public/carpool.js` 规则抽取 + 模型 `people` 补）→ 每个上车点、出发地、目的地都用百度地点核对（核对不上就提示换说法，不往下算）。
- 算法（`public/carpool.js` 纯函数，浏览器和 Node 共用）：
  - 接人顺序：≥ 2 人时用**批量算路**（驾车 N×N）枚举所有顺序，给三个选项：按你说的 / 最省时 / 最公平（坐车最久的人最短）；选中后用**路线规划 + 途经点**（`direction/v2/driving` 的 `waypoints`，按 `steps.leg_index` 拆成每一段）重算。
  - 倒推：目的地时间 − 到达留 10′ → 每段 × 1.15 缓冲 → 每站等 3′ → 每人「提前 2′ 下楼」；得到司机几点出发、每人几点下楼 / 车几点到 / 几点走。
  - 回程：散场时间按活动常见时长**假设**（看比赛 3 小时，卡片上写「假设 · 可改」），反着送，按途经点路线顺推。

## 7.8 v2.4 · M5 场景 3 开放式（画像 → 近期热点 → 分类菜单，2026-09-30）

- 入口：「我在上海多待两天，10月7号到8号，帮我安排，给点建议，我喜欢打网球和看展」→ 场景 3 → 先问日期 / 住处（订了没），再问一步「你喜欢什么、想排满还是松一点？」。
- **画像**：原话里说的兴趣直接记住（卡片上写「记住了：喜欢网球 · 09/30 的原话 ✕」，可删）；存在浏览器 `localStorage`，下一次开放式任务显示「之前说过」预选；节奏（松一点 / 排满）也记住。
- **近期热点**（`lib/hot.js` + `/api/hot`）：千帆百度搜索 `「上海 10月7日至10月8日 展览 市集 演出 活动」`，说了运动再搜 1 次 `「上海 网球 比赛 10月」`；ERNIE 只从结果里抽「活动名 / 日期 / 场馆 / 原文链接」，代码再校验：日期要覆盖你那几天、来源发布 60 天内、名称片段要在原文里出现、去重；场馆用百度地点检索核对，核对不上的丢掉。界面上每条写「来自网页 · 原文链接 · 发布于 … · 出发前看原文」，丢掉的也列出原因。
- **配额**：按文档每月免费 1500 次；应用自己限 300 次/月（`HOT_MONTH_CAP`），同一查询缓存 1 天（内存 + `data/hot/`）；界面和接口都显示「千帆百度搜索：本次 N 次（缓存命中 M）· 本月累计 · 免费额度 1500/月」。
- **主题**：ERNIE 给 2–3 个主题（「网球 + 看展的松弛两天」「光影戏剧与艺术漫步」），类别只能从固定分类菜单选（运动 / City Walk / 吃 / 展览演出 / 亲子 / 夜生活，`public/openplan.js` 的 `MENU`，每类的百度检索词是固定的）；代码校验（类别在菜单里、活动 id 存在、至少一个主题覆盖你说的兴趣，不够就补规则主题）。卡片写「大模型建议 · 地点会用百度检索核实」。
- **排天**（`OpenPlan.arrange`，纯函数）：每个类别百度检索（住处 12km）→ 按位置分成 N 片（每天一片）→ 活动放到日期覆盖、离当天那片最近的一天；离所有片都远的活动（实测「劳力士大师赛 @旗忠」）最多占一半的天，那天「围着活动场馆排」，并在场馆 5km 内**再检索**「餐厅 / 公园」（郊区场馆周边没有「本帮菜 / 历史文化街区」）；时段模板（松一点 3 段 / 排满 5 段），同一天类别不重样（网球一天最多 1 个），上一个点很长就顺延下一段，营业时间按顺延后的时间查。排好的点进入原来的流程：推荐酒店 → 时间轴 → 路线。

## 8. 已知不足

- ERNIE 任务解析 30–40 秒，演示时要等；输出每次略有不同（时间窗、追问措辞），关键字段由后端校验补全。
- 千帆 2026-09-29 下午曾返回 `403 Access denied due to overdue account`（账户欠费），v1.2 截图里的解析走了规则解析；充值后已恢复，v1.3 截图是真实 ERNIE。
- 场景 2：`direction/v2/driving` 不支持指定未来出发时间，打车用时是**查询时刻的实时路况**（页面写明查询时间），10-05 国庆当天实际可能不同；公交/地铁按指定日期时间查询。
- 场景 2：酒店名同音纠正（家庭→嘉廷）要用户确认；「换一家」的候选目前只显示文字，还不能点选替换。口述「普通美术馆」时百度首条是浦东美术馆，但 ERNIE 可能判成「普陀区美术馆」（普通≈普陀），也会标「请确认」。
- 场景 2：ERNIE 每次输出略有不同（活动重复、时长假设标记、类别），关键字段由后端修正；用户没说的时长（打球 2 小时、看比赛 3 小时）是假设，页面标注并追问；第二天结束后默认回酒店。
